Engine design package · 23 pages · one plan

3JSE

An open-source game engine and editor built around Three.js and WebGPU — not on top of a fork of them.

It exists to answer one question honestly: if Unreal Engine were invented today — for WebGPU, TypeScript, and AI-assisted development — what would it look like? The answer is not Unreal's UI redrawn in a browser tab. It is an editor, an object model, a scripting system, an asset pipeline, an AI-native command surface, and a web-first deployment story — all of them agreeing on one underlying representation of a game.

§ 01VISION.mdRead the full page →

The vision

Three.js already won the "does the web have a real renderer" argument. Nobody chooses Unity or Unreal over Three.js because Three.js renders badly — they choose it because Three.js stops being productive the moment you need a scene hierarchy you can see, gameplay logic you don't hand-wire, an asset pipeline that isn't a shell script, or a way for a non-programmer (or an AI agent) to safely change how the game plays. That gap — not rendering quality — is what 3JSE closes.

the core bet

3JSE is everything a renderer needs around it to become a platform — an editor, an object model, a scripting system, an asset pipeline, an AI-native command surface, and a deployment story a desktop engine cannot match. And it is designed in the era where a meaningful fraction of a game's code will be written by an AI agent operating the engine: every layer is built to be machine-readable and machine-editable first, human-friendly second — which, done correctly, produces an engine that is also unusually friendly to humans.

Four ways of working, one underlying game

3JSE is designed so that four different ways of working edit the same underlying game — never four parallel ones. This only works because of one canonical, typed, serializable representation of "what the game does" underneath all four: the 3JSE Gameplay IR.

🖱️Humans edit visually

Dragging assets, placing entities, adjusting values in an inspector, wiring nodes in a graph — a real desktop-class editor in the browser.

⌨️Programmers write TypeScript

The same components, systems, and APIs the editor and the graph compiler use. No separate "scripting language" to learn.

🔗Designers connect graphs

3JSE Graph is not a toy or a materials-only tool — it's a full authoring frontend for gameplay logic, compiling to the same IR as hand-written TypeScript.

🤖AI agents manipulate primitives

Entities, components, graphs, and assets through the same programmatic command surface the editor calls internally — never opaque code generation or simulated mouse clicks.

Non-goals — what 3JSE deliberately is not

✂️Not a Three.js fork

Three.js stays a normal, upgradable npm dependency. Any project can drop to raw Three.js at any layer, at any time.

🏰Not an Unreal clone

Where Unreal's design is excellent — Blueprints' expressiveness, a real content browser, construction/runtime duality — 3JSE preserves the capability, not the implementation. Where Unreal carries twenty years of C++ legacy, 3JSE deliberately does better.

🪞Not chasing Unreal's rendering ceiling

Nanite-class geometry and Lumen-class GI are not the fight this engine picks in its first several years. 3JSE's job is everything Unreal has besides the renderer.

🌊No one-size-fits-all world

3JSE does not assume every game is a giant open world — and does not assume every game is a tiny arcade demo either. The world system is unopinionated about both.

what success looks like

A developer with Blueprint, Verse, Unity, or Godot experience can open 3JSE and be productive within a day. A game built in 3JSE is, at every layer, a normal, readable, Git-diffable software project — never a proprietary binary blob only the editor can open. And an AI agent, given a one-sentence request, can operate 3JSE through the exact same primitives a human uses, produce a working change, verify it by actually running the game, and hand back something the human can keep editing normally — because "AI-native" means legible to both the AI and the human, not opaque to one of them.

Architecture — the ten layers

Most of the risk in an engine like this is coupling risk, not rendering risk — the danger that visual scripting, the AI layer, and hand-written code quietly drift into three different ways of expressing "what the game does." Putting the IR at the center is the one structural decision that prevents that drift; everything else follows from protecting it.

Layers 0–1 are the only ones a shipped game strictly needs at runtime. Everything above is development-time — and 3JSE Graph's compiled output (plain functions) ships, while the graph editor itself never does.

Six design principles

1Three.js is a dependency, never a fork

Imported like any npm package, pinned to a compatible range, upgraded like any dependency. Where Three.js doesn't expose something, 3JSE composes around it — not inside it.

2One IR, many frontends

TypeScript, 3JSE Graph, and AI generation all compile to the same 3JSE Gameplay IR. No subsystem may become a parallel, opaque execution engine.

3Everything the editor can do, code can do

Every editor mutation has a corresponding call in the runtime's command API. The editor is a GUI for that API — not a separate authority. This is what makes the Agent API possible without inventing a second interface.

4Plugins are first-class

The default engine is a curated set of official plugins on a small core. A third-party physics engine or gameplay package installs exactly the way an official one does.

5Projects are software projects

Scenes, prefabs, and graphs are readable, deterministically-serialized files under version control — never a proprietary binary only the editor can open.

6Features touch a small, predictable set of places

A command, a schema, a runtime system, an editor panel, inspector fields, optional graph nodes — not a scavenger hunt. A load-bearing constraint: 3JSE expects much of its own future development to be done by coding agents.

The 3JSE Gameplay IR (3IR)

The most important page in the design package. Every claim in the Vision — that visual scripting, hand-written TypeScript, and AI generation are "the same program" — is only true because of the architecture described here. Get this wrong and 3JSE Graph becomes exactly the isolated universe it is explicitly told not to become.

compiler framing

Treat gameplay authoring the way a real compiler treats source languages: multiple frontends, one intermediate representation, multiple backends.

TypeScript adapter
hand-written code
↘
3JSE Graph frontend
node canvas
→
3JSE Gameplay IR

→
JS/TS emitter
ships in game
↗
AI structured-gen

(future) Verse frontend
spacer
also emits: ▲ Interpreter (editor live-debug) · WASM emitter (hot-path opt-in) · Static analyzer (lint / AI context)

What 3IR actually is

A small, typed, JSON-serializable node-graph format. Deliberately narrower than a general-purpose AST — gameplay logic needs events, typed data flow, ordered side effects, branching, loops, async waits, and calls into the engine API. It does not need arbitrary closures over the JS module graph or dynamic eval.

type IRNode =
  | { kind: "event";    id; name; params: IRType[] }
  | { kind: "pure";     id; op;   inputs: IRRef[]; outputType: IRType }   // no side effects, fans out
  | { kind: "call";     id; target: EngineAPIRef; args; next: IRRef }     // the "exec wire"
  | { kind: "branch";   id; cond; then; else }
  | { kind: "loop";     id; over; body; next }
  | { kind: "await";    id; signal; next }
  | { kind: "variable"; id; scope: "local" | "component" | "resource"; type: IRType };

Every reference is typed — number, vector3, EntityRef, ComponentRef<Health>, domain enums, struct types generated from Component schemas. Type errors are caught at the IR level, before any backend sees the graph — which is why both the Graph editor and an AI agent get fast, structural feedback ("this pin wants a number, you connected a string") instead of a runtime TypeError three layers downstream.

What actually executes — two backends, same IR

🐞Interpreter — editor / live-debug

A tree-walking evaluator instrumented to report every intermediate value back to the editor. Slower, but every frame is fully inspectable — the correct tradeoff while iterating.

📦JS/TS emitter — shipping mode

The IR compiles ahead-of-time to a plain function — readable, formatted TypeScript a programmer wouldn't be embarrassed to have written — registered in the scheduler exactly like a hand-written System. No interpreter, no IR walking, no visual-scripting runtime tax in the shipped game.

Bidirectional graph ⇄ code editing

The TypeScript adapter parses a constrained, recognizable subset of TS into 3IR; the JS/TS backend emits back into that same subset with a source map — every emitted line carries a reference to the originating IR node, and every IR node to the graph node that produced it. A graph edit recompiles new text in the mapped region only; a text edit re-parses to a new IR subgraph and the graph view updates live. The moment code leaves the recognized subset, it renders in the graph as an opaque Code node — a typed black box the graph can wire into but not decompose. That mirrors Unreal's Blueprint/C++ boundary, made visible instead of silently desyncing.

why not "the graph just emits JS"?

The tempting shortcut — the graph editor emits JS text directly, as most visual-scripting-on-the-web tools do — is rejected deliberately. It would satisfy "compiles to clean JS" and fail everything else: AI structured generation needs a typed target it can validate before anything executes; live debugging needs a structured graph to instrument; bidirectional editing needs a common structural form both sides can convert to losslessly; and a future Verse frontend needs a target that isn't JavaScript's syntax specifically. 3IR is more upfront design work — and it is the reason 3JSE Graph does not become an isolated universe.

05 · Object model
§ 05ENTITY_COMPONENT_MODEL.mdRead the full page →

The object model

3JSE uses a hybrid Actor/Component authoring model backed by ECS-style storage — not pure ECS, not classic OOP inheritance, and not a thin wrapper that renames Object3D. An Entity behaves like an Actor/GameObject/Node to a human or an AI reading the project, and like an ECS row to the scheduler at runtime. Nothing about this is a compromise — it's a deliberate separation of authoring ergonomics from storage layout.

TermWhat it is
WorldThe runtime container for all loaded Levels, the Resource/Service registry, and the scheduler. One per running game.
LevelA serializable unit of content — Entities plus level-local settings. A World can hold several loaded at once.
EntityAn addressable, named "thing": stable ID, optional Transform (backed by an Object3D), a set of Components. Directly analogous to an Unreal Actor, Unity GameObject, or Godot Node.
ComponentTyped data attached to an Entity — Health, CharacterController, Inventory. Pure data by convention; behavior lives in Systems or Behaviors, so components stay serializable and diffable.
SystemLogic that runs each tick over every Entity matching a component query — the ECS half of the model. Hand-written (TypeScript) or generated (compiled 3JSE Graph).
BehaviorA Component that also names a Graph or a small TS function to run for that entity specifically — the "attach a script to this one object" workflow, expressed without inventing a second execution model.
PrefabA serialized Entity (with children) usable as a template; instances track their source and can override fields — matching Unreal's Blueprint-instance and Unity's Prefab-override model.
ResourceGlobal, non-spatial data not owned by any single Entity (input state, audio mixer settings).
ServiceA Resource that also exposes an imperative API — SaveService.save() — alongside its data.

Storage — why this is legible to an AI and a human skimming a diff

Components of the same type are stored contiguously (archetype/SoA storage), so a System querying (Transform, Velocity) iterates a tight, cache-friendly array — the specific mechanism that makes "editor-friendly" and "fast at 10,000 instances" compatible rather than contradictory. Object3D is the storage for the Transform component specifically, so every existing Three.js library keeps working. The point of the shape: a serialized Entity reads as a sentence, not a call stack.

{
  "name": "Player",
  "components": {
    "Transform":            { "position": [0, 1, 0] },
    "CharacterController":  { "maxSpeed": 6, "jumpHeight": 1.4 },
    "Health":               { "current": 100, "max": 100 },
    "Inventory":            { "slots": 8, "items": [] },
    "AnimationController":   { "graph": "player_locomotion.3jgraph" },
    "GrapplingHook":         { "range": 25, "reelSpeed": 12 }
  }
}

Serialization, hot reload, and networking fall out of the same choice

💾Serialization

Components must be plain JSON-compatible data, enforced by the component schema system. A type declares its fields once — the inspector, the serializer, and the network replicator all derive from that single schema.

🔥Hot reload

Systems are registered by name/reference and Components are plain data — redefining a System's logic never invalidates existing Entity data.

🕸️Networking

Replication is just "which Components, on which Entities, does this client need diffs for" — a direct consequence of Components being the atomic unit of state.

🪟Inspector

Generated directly from each Component's schema — no per-component custom UI to hand-write unless a component opts in for a bespoke editor (a curve, a gradient).

It does not claim to be the fastest possible ECS — a hand-tuned Bevy/bitECS engine will out-iterate it in a synthetic benchmark. It optimizes for the actual bottleneck in practice: how long it takes a human or an AI agent to understand and safely change what an entity does.

The runtime

@3jse/runtime is the only package a shipped game strictly depends on besides three. It owns the tick loop, the World/Level/Entity/Component model, and the boundary where 3JSE's abstractions hand off to raw Three.js. 3JSE does not replace any Three.js concept that already works — it adds inspectable, serializable, schedulable structure around it.

The tick loop

requestAnimationFrame / fixed-step accumulator
↓
1 · Input sampling
@3jse/runtime input resource
↓
2 · Fixed-step systems
physics, gameplay logic — deterministic order
↓
3 · Variable-step systems
camera, animation blending, particles
↓
4 · 3JSE Graph tick
compiled Behavior functions, event dispatch
↓
5 · Render systems
culling, LOD select, render-graph submit
↓
6 · Late / post systems
UI layout, audio listener update

Systems declare which stage(s) they run in and which archetypes they read/write; the scheduler topologically sorts by data dependencies and parallelizes across Web Workers where possible. Fixed-step logic runs on an accumulator decoupled from refresh rate — deterministic per machine regardless of frame rate.

🔥Hot reload is a function swap

Compiled Behaviors are registered as named function references, not baked into entity construction. Editing a system's TS source — or recompiling a Graph — replaces the registered function and the next tick picks it up. No scene reload, no lost state. This is the mechanism behind Edit → Play → Pause → Inspect → Modify → Resume.

🎯Determinism posture

Fixed-step gameplay/physics is deterministic per machine — sufficient for save/replay and single-machine time-travel debugging. Explicitly not cross-platform bit-exact, so networking uses state replication instead of lockstep.

🧪Headless mode

No hard dependency on a DOM or a visible canvas. Boots against an offscreen canvas for CI, automated tests, and the AI Agent API's verification loop. A first-class mode — 3jse run --headless.

🚪Escape hatch

A project can always drop one level down: get the raw Object3D for any entity and hand-write Three.js against it. Nothing requires going through 3JSE's API exclusively — the release valve that keeps 3JSE from becoming a second thing to fight.

07 · Editor
§ 07EDITOR.mdRead the full page →

The editor

A single-page application built on the exact same @3jse/runtime a shipped game uses, running the actual WebGPU viewport in-process — no separate game process, no IPC. One codebase distributes three ways: browser (quick edits, sharing a project link, CI-driven visual review), Tauri desktop app (the primary target for serious work — native filesystem, multiple windows, better GPU access), with Electron as a viable fallback shell. Games built with 3JSE never depend on the editor at runtime.

the central promise

Edit → Play → Pause → Inspect → Modify → Resume. Play mode runs the same World in the same WebGPU context — entering Play does not serialize the scene out to another process. Pausing freezes tick advancement, not the World's data: change jumpHeight from 1.4 to 2.2 mid-jump and resume — current velocity and position are untouched, only the constant driving future jumps has changed. Open the Graph debugger mid-bug, see exactly which branch fired last frame with real captured values on the wires, patch it, resume without restarting the level.

Panel inventory — all 22, all dockable, all plugin-registered

Panels are declared through the same panel-registration API third-party plugins use — there is no "built-in panel" privilege tier. The Agent Panel is a permanent dock, not a floating chat widget: it shows the agent's plan, the tool calls it's making against the same command API, and a running diff — reviewable and revertible through the same undo stack as a manual edit.

🧰Multi-scene

Multiple Levels can be open at once; the Hierarchy scopes to the active Level while allowing cross-level entity references where the World architecture permits.

🌿Git, not CRDT

No live multi-user CRDT collaboration for the first several years. Collaboration is Git-based — branches, PRs, merge conflicts a human resolves in a real diff. A deliberate, simpler bet that costs nothing to build and is the model most target developers already trust.

Exiting Play can optionally keep the resulting state ("apply Play state to Level") instead of always discarding it.

08 · Visual scripting
§ 08VISUAL_SCRIPTING.mdRead the full page →

3JSE Graph — visual scripting

A node-graph authoring frontend for 3JSE Gameplay IR — not a separate execution engine. Every capability exists because it's expressible in 3IR; there is no Graph feature hand-written TypeScript can't also express, and no TypeScript-callable engine API a graph node can't call. That symmetry is deliberate: it's what keeps this from becoming "its own isolated universe" — the one thing the design brief calls out to avoid above all else.

14 node families, typed pins throughout

📡Events

The AI Agent API

3JSE is built in the era where a meaningful share of its own use — and its own future development — will be done by an AI agent. The Agent API therefore cannot be a bolted-on chat feature with its own bespoke access path. It is the same command surface the editor itself is built on, exposed as an MCP-shaped local tool server (@3jse/agent) — so any MCP-capable agent, not just a bespoke in-editor chatbot, can drive a 3JSE project. An agent that calls scene.mutate is doing exactly what a human dragging a slider caused to happen — through the identical code path, landing in the identical undo history.

why verify matters

The verify step is the difference between "code that compiles" and "a change that actually works" — the loop always includes an actual headless run, not just a type check. A change can typecheck cleanly and still throw at runtime, render a blank viewport, or silently do nothing — and getConsole, getPerf, and captureFrame are positioned to catch each before a human ever sees the failure.

Worked example — the shark

"Make this shark patrol this area until it sees the player, then chase them. If it gets harpooned, allow it to tow the player."

1 · scene.query the Shark 2 · add Perception + NavAgent 3 · graph.write patrol→chase tree 4 · wire Harpoon.onHit → Tow state 5 · animation transitions 6 · RigidBody + constraints 7 · runtime.run(headless) 8 · getConsole → find missing ref 9 · repair the transition 10 · re-run, captureFrame, report

At every step the agent used tools a human could have triggered from the Inspector, the Graph editor, or the Console. Natural-language project creation is the same loop at project scope: parse intent → select the closest genre template → decompose into ACT/VERIFY steps — and hand back real Entities, real Components, real Graphs, browsable in the ordinary editor. A hard constraint, not an aspiration: any AI output that can't be inspected and edited through the same panels a human uses is treated as an Agent API bug.

Trust tiers and structural guarantees

💬Suggest

Every change is proposed as a diff/graph patch; nothing lands without explicit approval.

🛠️Co-pilot

Free to make local, additive, reversible edits. Deletions, breaking API changes, and new dependencies still require approval.

🤖Autonomous

CI-style batch jobs on a sandboxed branch; output lands as a change-proposal merged through normal Git — never a silent direct commit.

Guarantees independent of tier: every agent mutation lands in the same undo/version history as a manual edit; generated TypeScript runs in a capability-scoped sandbox (no network, no filesystem outside the project tree); secrets are excluded from what the agent can read; and scope limits (files touched, entities mutated per turn) are configurable — a Suggest-tier session fixing one bug can't touch two hundred files without a visible, flagged deviation from plan.

Why this doesn't need a second engine: because the tool surface is the editor's own command API, there was no temptation to build a parallel "AI scripting language" or a simulated-input automation layer. The Agent API mostly assembles pieces the rest of the engine already required — typed validation, headless verification, undo-integrated history — into a loop, rather than inventing new ones.

Plugin architecture

3JSE expects a significant share of its own future feature development to be done by coding agents, and expects third-party packages to be genuinely first-class rather than a tolerated extension mechanism. Both goals fail unless adding a subsystem is a small, predictable, well-bounded operation — the opposite of "understand the whole engine first." This page specifies that boundary.

Ten extension points — the same ones official packages use

🧱Component schemas

New Component types with field types, defaults, validation — instantly inspectable, serializable, replicable.

⚙️Systems

Tick-stage-scoped logic over a component query.

🌐Resources / Services

Global singletons, registered once on the World.

🔗3JSE Graph nodes

New node types, auto-derived from Component/event schemas where possible.

✨Material Graph nodes

New shading node types compiling into TSL.

🖥️Editor panels

New dockable panels — the same registration API every built-in panel uses.

🎛️Inspector field renderers

Custom widgets for specific field types — a curve editor, a gradient picker.

📦Importers / Exporters

New Asset Pipeline format handlers.

🤖Agent tools

New MCP-shaped tools extending the Agent API for package-specific operations.

🚀Build targets

New deployment targets.

A minimal plugin might register just a Component schema and a couple of Systems; a subsystem-scale plugin like @3jse/terrain registers schemas, Systems, editor panels, Material Graph nodes, and an importer — through the exact same manifest shape. Scale changes how many extension points a package uses, not the mechanism.

Build, wrap, adopt — or leave alone

RenderingAdopt Three.js WebGPURenderer / TSLAlready excellent — already the reason developers choose the web for 3D.
PhysicsWrap Rapier default, Jolt alternativeMature, fast WASM options; no reason to reimplement.

stability & trust

Extension-point APIs are versioned independently of the engine, with semver guarantees per point — a breaking change to the Component-schema API is a major bump on that API specifically. Plugins declare which API versions they target; the editor warns rather than silently fails. And plugin code runs under the same capability scoping as agent-generated code — an importer needs file read access to the asset being imported; a gameplay package needs none. Neither AI agents nor third-party authors should be implicitly trusted with more access than the extension point they're using actually needs.

12 · Project format
§ 12PROJECT_FORMAT.mdRead the full page →

Project format

A 3JSE project must be readable, inspectable, Git-friendly, diffable, portable, and recoverable without the editor. Every choice below is in service of those six words — none are negotiable trade-offs against "a binary format would be faster," because none of the operations that matter actually require one.

Directory layout

/project
  /assets            meshes, textures, audio, fonts
  /scenes            Level files
  /prefabs           Prefab files
  /graphs            .3jgraph files
  /materials         Material Graph files
  /scripts           hand-written TypeScript
  /systems           compiled output ("ejected" graphs)
  /ui                UI/HUD layouts
  /audio             mixer bus config
  /plugins           project-local plugin packages
  project.json       engine version, deps, targets, tiers

Serialization rules

Deterministic key ordering — fixed, schema-defined order, so a value change produces a one-line diff, not a reshuffled file.

Stable IDs, not array position — ULID-style IDs generated once at creation; reordering a list never looks like every element changed.

Human-readable JSON — pretty-printed, not minified, not a binary pack. Any text editor, and any AI agent's plain file-read tool, can understand a scene file.

Binary payloads stay binary — referenced by path/hash (asset://<hash>), so a texture re-export is one changed binary file, not a giant base64 diff.

{
  "kind": "Level",
  "id": "01J8Z…",
  "name": "MainMenu",
  "entities": [
    {
      "id": "01J8ZA…",
      "name": "Player",
      "components": {
        "Transform": { "position": [0, 1, 0], "rotation": [0, 0, 0, 1] },
        "CharacterController": { "maxSpeed": 6, "jumpHeight": 1.4 },
        "Health": { "current": 100, "max": 100 }
      }
    }
  ]
}

There is deliberately no separate "runtime scene format" a build step converts this into — the same JSON structure that's diffable in a PR is what the runtime loads. And recoverability: a developer who has lost access to 3JSE entirely can still read exactly what a scene contained, hand-edit a Component value in a text editor, and boot the game from @3jse/runtime with no editor installed at all. Two developers' changes to different Entities merge cleanly at line level; a genuine conflict shows up as an ordinary, human-resolvable Git conflict marker in readable JSON.

13 · Asset pipeline
§ 13ASSET_PIPELINE.mdRead the full page →

Asset pipeline

Dragging a file into the Content Browser should produce something closer to "imported and understood" than "copied and referenced." The pipeline runs identically in the editor (drag-and-drop), headless (CLI/CI), and under agent control (assets.import) — one implementation, three callers.

🗂️Supported formats
Meshes: glTF/GLB · FBX · OBJ · USDZ* Textures: PNG · JPG · KTX2/Basis · HDR/EXR Audio: WAV · MP3 · OGG Video: MP4 · WebM Fonts: TTF/OTF + MSDF Anim: in glTF/FBX

GLB/glTF is the native, best-supported path. FBX/OBJ/USD exist for import convenience, converting into 3JSE's own internal representations. *USD: import-only, a practical geometry+material subset.

What "analyze" means — suggestions, not silent mutation

🧍Character detection

A rigged mesh with a recognizable humanoid/creature bone hierarchy is flagged as "likely a character" and offered a starter Entity — the literal "drag a rigged GLB in and 3JSE understands" behavior, implemented as bone-naming heuristics, not a black-box ML classifier.

🦴Skeleton & animation

Separates static from skinned meshes, groups clips by armature, offers clip renaming/retargeting.

🪜LOD generation

2–3 automatic mesh-simplification tiers (configurable), with a human able to author custom LODs instead.

🗜️Texture compression

Transcodes to KTX2/Basis at build time per platform target — the source texture is preserved and re-transcoded whenever the target matrix changes.

📐Mesh compression

Draco or meshopt encoding for delivery size, chosen per streaming needs.

🧲Collider generation

Convex-hull or simplified-mesh collider suggestions for the physics engine, offered alongside rather than assumed identical to the visual mesh.

🖼️Thumbnails

Rendered automatically for the Content Browser at import time and cached.

📊Metadata & dependencies

Bounding box, triangle/material/bone counts, source hash — surfaced to the Inspector and to scene.query so an agent can reason about asset cost without loading it. Every asset records what it references and what references it.

Imported assets are content-addressed internally (a hash of the source file) so re-importing an identical file is a no-op — an implementation detail of the cache that never leaks into how a developer browses the project.

14 · Rendering
§ 14RENDERING.mdRead the full page →

Rendering

3JSE does not build a renderer. It builds an authoring and orchestration layer on top of Three.js's WebGPURenderer (with WebGL2 as its existing automatic fallback) — a Material Graph, a render-pass graph, and quality tiers. This is the same architectural principle as the IR applied to shading: one canonical representation instead of a second parallel compiler.

the material graph

A visual node editor, analogous in day-to-day usability to Unreal's Material Editor, that compiles into Three.js's own TSL node system — not WGSL/GLSL text from a competing implementation. Three.js already did the hard cross-backend compiler work: one authored graph runs on both WebGPU (WGSL) and WebGL2 (GLSL) automatically. The WebGL2 fallback never requires a parallel authoring path.

PBR building blocks texture sampling · triplanar procedural noise math normals / displacement vertex animation (wind, waves) transparency / blending post-processing stack compute nodes (opt-in) plugin-registered custom nodes
📋Render graph & tiers

An ordered render-pass graph (opaque → transparent → post-process, plugin-registerable — e.g. @3jse/water's refraction pass), plus quality tiers that scale shadow resolution, post-processing, particle density, and LOD bias together as one selectable unit.

☀️Environment & lighting

Sky/HDRI, fog, and lighting presets on top of Three.js's existing light types — orchestration and presets, not new lighting math. GI beyond Three.js's roadmap is explicitly out of scope for the early phases; 3JSE tracks and adopts Three.js's own capabilities as they mature.

15 · Physics
§ 15PHYSICS.mdRead the full page →

Physics

Physics simulation is exactly the kind of subsystem the build/wrap/adopt framework says not to build from scratch — a solved, hard problem with mature WASM-compiled options. 3JSE ships Rapier (Rust → WASM) as the default backend via @3jse/physics-rapier, with Jolt as a swappable alternative for projects that need its specific character-controller or large-scene characteristics. Both implement the same @3jse/physics interface — swapping backends is a package swap, not a rewrite of gameplay code.

🧱Bodies are Components

RigidBody, Collider, Joint — inspectable, serializable, replicable like anything else. The physics step runs as a fixed-step System; a sync System writes transforms back to each Entity's Object3D, so render/animation/camera always see current-frame results.

🧰Collision editing

Gizmos for box/sphere/capsule/convex-hull colliders, compound colliders, and constraints — gizmo-first, with exact numeric entry in the Inspector, seeded from the asset pipeline's suggestions.

🧵Threading

Simulation runs off the main thread via a Web Worker — SharedArrayBuffer where cross-origin isolation allows, structured-clone message passing otherwise. The main thread stays free for rendering and input.

🔍What 3JSE adds

A uniform query API (raycast, overlap, sweep) for TS and Graph nodes alike; collision/trigger events surfaced as 3IR events (OnCollisionEnter) so gameplay logic never touches the WASM API; per-machine determinism for save/replay — explicitly not cross-platform bit-exact.

16 · Animation
§ 16ANIMATION.mdRead the full page →

Animation

3JSE builds directly on Three.js's AnimationMixer and AnimationClip for clip playback and blending primitives — and adds the authoring and orchestration layer Three.js deliberately leaves to the application: state machines, blend trees/spaces, retargeting, and IK, all as a specialized 3JSE Graph scope sharing the same IR and debugger.

🔁State machine nodes

States hold a clip or blend tree; guarded transitions with typed conditions against Component fields (Speed > 0.1); entry/exit events fire as ordinary 3IR events other graphs can listen to.

🌗Blend trees / spaces

1D (walk↔run by speed) and 2D (move-direction blend space) nodes sampling multiple clips into a weighted pose.

🎯Sync / event nodes

Notify-style markers on a clip (footstep, hit-frame) surface as 3IR events — spawn a footstep VFX or apply damage on a hit-frame without polling animation state.

🦿IK nodes

Two-bone IK, look-at aim, foot-placement/ground-adaption — layered on top of the base pose.

🧍Skeletal retargeting

A named humanoid bone-mapping standard lets a clip authored on one skeleton play on another via a retarget map — generated automatically when skeletons match the standard. This is what makes template character controllers usable with a project's own custom mesh.

⚡Performance

Skinning is GPU-driven; crowds of simultaneously-animated Entities are a documented target for the WASM emitter path and instancing — not a default requirement for typical character counts.

The world system

The deliberate non-assumption: a tiny arcade game, a Crash Bandicoot-style level select, a KOTOR-style sector game, a large streamed environment, and a Roblox/UEFN-style hub of experiences are all the same underlying mechanism configured differently — not five separate features.

Sector-based (KOTOR-style)One World, sectors = discrete zones, portal-triggered transitions with a loading Level.

19 · Networking
§ 19NETWORKING.mdRead the full page →

Networking

Honest up front: this covers gameplay networking (client/server multiplayer for a shipped game), not editor collaboration — and it does not promise deterministic lockstep. Because the runtime's fixed-step simulation is per-machine deterministic, not cross-platform bit-exact, the default model is state replication with server authority — the same category of approach Unity, Unreal, and most shipped web multiplayer games actually use.

why replication fits without extra machinery

Because gameplay state already lives in typed, schema-declared Components, replication is "which Components, on which Entities, does this connection need diffs for" — not a parallel serialization system bolted on afterward. A Component opts in with a schema flag, and @3jse/networking tracks per-field dirty state each tick (cheap — storage is already columnar), serializes only changed fields per connection, and interpolates/extrapolates on the client with per-Component override for fields that should snap (like AnimationState).

👑Authority model

Server-authoritative by default; client-side prediction + reconciliation for the locally-controlled player (PredictedController, implemented once — input applied immediately, corrected against the authoritative snapshot). RPCs via IsServer/IsClient guard nodes for one-off events that don't fit the continuous-diff model.

🔌Transport

WebSocket by default (broad compatibility, simplest server deployment); WebRTC data channels as a plugin-swappable transport for lower-latency setups. The transport is an interface, not a hardcoded assumption.

🧩Core vs plugin

@3jse/networking ships the replication core, authority model, and RPC nodes — enough for the Multiplayer template to work out of the box. Matchmaking, dedicated-server orchestration, and rollback netcode for competitive action are explicitly not core: documented extension points until real usage shows which are worth standardizing.

Performance

Performance work is not a late optimization pass — it's a set of architectural decisions made early enough that most projects never have to fight the engine to hit a reasonable budget, plus honest, visible instrumentation for the projects that need to go further. WebGPU is primary; WebGL2 is a permanent second render path, not a temporary bridge.

TechniqueMechanism
Spatial partitioningBVH-backed frustum/occlusion culling, rebuilt incrementally as Transforms change.
InstancingAutomatic InstancedMesh promotion for repeated Prefab instances above a threshold (foliage, crowds, projectiles).
BatchingStatic-geometry merging at build time, not at runtime cost.
LODPipeline-generated tiers selected by screen-space size, cross-faded to avoid popping.
Occlusion cullingSoftware occlusion (hierarchical depth buffer) as portable baseline; hardware queries as an extension point.
Texture compressionKTX2/Basis universal, transcoded per target format at build time.

Workers & quality tiers

🧵Three worker lanes

Physics on a dedicated worker (SharedArrayBuffer where isolation headers allow); asset decoding/transcoding on loader worker pools; and the 3IR WASM emitter as a defined escape hatch for gameplay logic that genuinely profiles hot — deliberately not the default, because most gameplay logic's bottleneck is elsewhere.

📊Quality tiers

Low / Medium / High / Ultra — each a coordinated bundle: shadow resolution and cascades, post-processing set, particle density, LOD bias, instancing threshold, physics substep count all move together. The default experience is "pick a tier," not "tune forty knobs" — and the Mobile template starts conservative instead of discovering the need after shipping.

🌍Large worlds

World Partition streaming plus asset streaming keep the per-frame and memory budget a function of streaming radius and quality tier, not total authored content — the property that makes "large worlds" and "runs on a mid-range laptop" compatible goals.

⏱️Shader compilation

TSL materials compile to WGSL/GLSL ahead-of-time at build wherever inputs are static; the Material Graph lints graph structures that imply runtime branching and compile stalls — surfaced at build time, not discovered as a hitch during play.

Build & deployment

This is the area 3JSE can beat Unreal outright, not just match it — the web's distribution model is structurally better: no multi-gigabyte installer, no store review cycle standing between a build and a player for the default target. 3JSE's job is not inventing this advantage; it's not squandering it.

▶️Play never builds

Pressing Play boots the current World directly in the same WebGPU context the editor uses — instant by construction.

📦Publish does it properly

Publish is a separate problem with different priorities — smallest, fastest, most compatible output:

1. Tree-shaking — only packages a project actually uses are bundled.
2. Asset finalization — textures transcoded per target, meshes compressed, unused LOD tiers dropped.
3. Graph compilation — every 3JSE Graph compiles to JS/TS backend output: zero interpreter, zero visual-scripting runtime tax.
4. Code bundling — esbuild/rollup-class, minified, code-split by Level/sublevel so the initial download isn't the whole game.
5. Manifest generation — exact asset hashes for CDN cache-busting and agent build verification.

Target matrix — one build, six wrappers

TargetMechanismPosture

PWAStatic output + manifest/service-worker for offline play and install-to-homescreennear-term
DesktopTauri shell wrapping the static build — native filesystem/savenear-term
SteamDesktop build + Steamworks (achievements/cloud-save bridged to @3jse/achievements/@3jse/save)mid-term
MobileTauri-mobile / Capacitor-class wrapper; aggressive default quality tiermid-term, tracked honestly

Every tier above "static web" is a wrapper around the same build, not a divergent platform-specific codepath — the concrete meaning of "the browser is not a limitation to apologize for." Quality tiers are resolved partly at build time: a mobile build isn't shipping desktop-resolution textures it will never use, and a desktop build isn't capped at mobile settings by default.

§ 23VERSE_COMPATIBILITY.mdRead the full page →

Verse compatibility

Verse is Epic's programming language for UEFN — designed around determinism, gameplay-suited concurrency, and a strong type system. It is not open, not portable outside Epic's ecosystem, and its runtime is not something 3JSE can or should depend on. The question this page answers is narrower than "should 3JSE support Verse": it's which parts of Verse's design are worth deliberately resembling, independent of Epic's implementation.

LevelDescriptionVerdict
0 — No compatibilityScripting concepts owe nothing to Verse.Rejected — Level 1 costs nothing and has real upside.
1 — Conceptual mapping3JSE's concepts map cleanly onto Verse's mental model, though nothing compiles between them.Adopt — close to free; a Verse developer recognizes 3JSE Graph within minutes.
2 — Verse-inspired syntax → 3IRA textual frontend using Verse-like syntax (not Verse itself) compiles into 3IR.Future frontend — a new IR-producer, not a re-architecture.
3 — Import a portable Verse subsetParse a genuinely portable subset of real Verse source into 3IR.Investigate — a Phase 0 research spike; depends on Epic's published spec/licensing.
4 — Emulate selected Verse APIsShim well-known Verse stdlib functions/effects.Reject as priority — highest cost, lowest value; syntax-compatible but not platform-compatible.
5 — Full Verse runtimeRun actual Verse programs, unmodified, against 3JSE.Reject — would re-introduce a second competing execution engine alongside 3IR.
the recommendation

Target Levels 1–3; do not build 4 or 5. Levels 1–2 are essentially free extensions of decisions 3IR already made for unrelated reasons — a typed, frontend-agnostic IR was going to exist regardless of Verse. Level 3 is worth a scoped research spike but not a commitment. Levels 4–5 would make 3JSE strategically dependent on Epic's roadmap and licensing to deliver a compatibility promise that can't actually be kept in full — a Verse script's behavior depends on UEFN's surrounding platform, not just its syntax.

Verse concept3JSE equivalent (Level 1)
class with var/const fieldsComponent schema
Effects (<transacts>, <varies>)3IR's pure vs. impure node distinction
spawn / concurrency blocks3JSE Graph async nodes / coroutine-style yields

This table is documentation, not a compatibility shim — its value is making a Verse-literate developer's existing mental model transfer to 3JSE quickly, which is the actual goal the Vision sets, not source-level interoperability with Epic's ecosystem.
